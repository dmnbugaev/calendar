# Безопасная синхронизация расписания

Синхронизация расписания группы 251-362 в Google Calendar должна быть предсказуемой и обратимой. Ошибки источника не должны разрушать календарь пользователя.

## КРИТИЧЕСКОЕ ПРАВИЛО

**Неполный, пустой или ошибочный ответ университета НИКОГДА не должен приводить к массовому удалению событий.**

- Если источник вернул пустой список, ошибку, частичные данные или ответ не прошёл Zod-валидацию — синхронизация останавливается полностью, события не трогаются.
- Удаление допустимо только для событий, у которых есть наш маркер в `extendedProperties.private`, И когда источник вернул **полный валидный** набор данных, И число удаляемых событий не превышает разумный порог (например, > 50% существующих помеченных событий — требуй явного подтверждения пользователя).
- Никогда не удаляй события, созданные пользователем вручную (без нашего маркера).

## Идемпотентность и идентификаторы

- Каждое занятие получай **стабильный детерминированный ключ** из данных расписания: например `hash(группа + дата + время начала + время конца + дисциплина + преподаватель + аудитория)`. Одинаковый урок всегда даёт одинаковый ключ.
- Ключ записывай в событие при создании: `extendedProperties.private.unicalendarKey = <ключ>`.
- Повторный запуск синхронизации на неизменённых данных не должен менять события (zero diff).

## Сопоставление и изменения

- Перед изменениями выгружай существующие события календаря (`events.list` с пагинацией) и индексируй их по `unicalendarKey`.
- Нормализованный payload занятия сериализуй и сравнивай с хранённым хешем (`extendedProperties.private.payloadHash`) — обновляй (`update`) только при реальном изменении; отсутствующее событие создавай (`insert`); лишнее помеченное — удаляй (`delete`).
- Дубликаты невозможны по построению: перед `insert` проверяй индекс; при обнаружении дубликата в календаре — исправляй его (merge), а не добавляй ещё один.

## Надёжность

- Обрабатывай частичные результаты: если часть операций в пакетах упала — фиксируй успешные, повтори только упавшие при следующем запуске (идемпотентность это позволяет).
- Повторы Google API — с экспоненциальной задержкой (см. skill `google-calendar-oauth`).
- **Конкурентные запуски**: перед синхронизацией бери блокировку (строка/флаг в PostgreSQL или advisory lock). Второй запуск во время первого — отклоняется с понятным сообщением.
- **Журналирование**: каждую синхронизацию записывай в БД — время, статус, счётчики (создано/обновлено/удалено/пропущено), детали ошибок. По журналу пользователь должен понимать, что произошло.
- Большие объёмы — батчами с ограничением скорости, чтобы не упереться в квоты.

## Запрещено

- Использовать `id` или `iCalUID`, сгенерированные «на лету» нестабильно (случайные элементы в хеше: порядок полей, локаль, текущее время).
- Удалять события по признаку «не нашёлся в источнике» при подозрении на неполноту данных.
- Запускать destructive-операции против календаря без журналирования.
